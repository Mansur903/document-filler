# Design

## Context

См. `proposal.md` и три delta-спецификации. Сейчас Angular `App` хранит одну реактивную форму, выбранный тип документа передаётся через IPC в Electron, а Python OCR возвращает строго определённый набор строковых полей. `passport-ocr.service.ts` проверяет полный состав ответа; `document-generation.service.ts` использует явный список полей. Правая панель имеет собственную прокрутку, а тип документа выбирается слева до распознавания. Кириллическая OCR-модель уже входит в локальный пакет.

## Goals / Non-Goals

**Goals:**

- Встроить оба типа свидетельств в действующий локальный поток выбора файла, OCR, слияния данных и генерации DOCX.
- Сохранить однозначность данных каждого лица и документа в форме и плейсхолдерах.
- Дать пользователю удобную проверку многочисленных полей без постоянного удлинения правой панели.

**Non-Goals:**

- Автоматически определять тип загруженного документа.
- Сверять записи ЗАГС с государственными реестрами или подтверждать юридическую подлинность документа.
- Автоматически связывать ребёнка или супругов с владельцем ранее распознанного паспорта.

## Decisions

### 1. Отдельные контракты и имена полей

Добавить типы `russianBirthCertificate` и `russianMarriageCertificate` в Angular, Electron и Python. Ввести по отдельному полному OCR-контракту для каждого типа. Все ключи начинаются с `birthCertificate` либо `marriageCertificate`, чтобы повторяющиеся ФИО, даты и номера не попадали в общие паспортные поля. ФИО разбивается на фамилию, имя и отчество; при отсутствии отчества остаётся пустое значение. Для супругов использовать нейтральные `Spouse1` и `Spouse2` в порядке документа; для родителей — `Father` и `Mother` по соответствующим разделам. Названия ключей фиксируются ниже и используются без преобразования как DOCX-плейсхолдеры.

| Группа | Ключи |
| --- | --- |
| Ребёнок | `birthCertificateChildSurname`, `birthCertificateChildGivenName`, `birthCertificateChildPatronymic`, `birthCertificateChildDateOfBirth`, `birthCertificateChildPlaceOfBirth` |
| Отец / мать | Для `Father` и `Mother`: `birthCertificate{Role}Surname`, `GivenName`, `Patronymic`, `DateOfBirth`, `Citizenship`, `Nationality` (полный префикс повторяется в каждом ключе) |
| Регистрация рождения | `birthCertificateRegistrationDate`, `birthCertificateRecordNumber`, `birthCertificateRegistryOffice`, `birthCertificateIssueDate`, `birthCertificateSeries`, `birthCertificateNumber` |
| Каждый супруг | Для `Spouse1` и `Spouse2`: `marriageCertificate{Role}SurnameBefore`, `GivenNameBefore`, `PatronymicBefore`, `DateOfBirth`, `PlaceOfBirth`, `Citizenship`, `Nationality`, `SurnameAfter` (полный префикс повторяется в каждом ключе) |
| Регистрация брака | `marriageCertificateMarriageDate`, `marriageCertificateRecordDate`, `marriageCertificateRecordNumber`, `marriageCertificateRegistryOffice`, `marriageCertificateIssueDate`, `marriageCertificateSeries`, `marriageCertificateNumber` |

Для парного имени `GivenNameBefore` и отчества `PatronymicBefore` сохраняется добрачная запись, как она указана в документе. Не выводить поля одного лица из другого. Альтернатива — переиспользовать общие `surname`/`dateOfBirth`: это теряет принадлежность значения и может затереть паспортные данные.

### 2. Парсеры по названиям реквизитов и геометрии

Повторно использовать кириллический профиль PaddleOCR и существующую загрузку JPG/JPEG/PNG/PDF. Для каждого типа создать отдельный парсер поверх `OcrTextBlock` с нормализацией переносов, падежных форм названий реквизитов, числовых серий и вариантов дат. Сначала проверить характерные заголовки и якоря документа, затем выделить области ребёнка/родителей или супругов/регистрации и соотнести ближайшие значения с названием реквизита. Различать `дата заключения брака` и `дата составления актовой записи`, `номер актовой записи` и `номер свидетельства` по контексту, не только по числовому шаблону. В PDF рассматривать страницы по отдельности и объединять только совместимые фрагменты одного свидетельства; посторонние страницы игнорировать. При конфликте кандидатов оставлять спорное поле пустым.

Календарные даты возвращать в `YYYY-MM-DD`, невалидные — `null`. Серию сохранять как текст с буквенными символами и дефисом после нормализации пробелов; номер свидетельства не смешивать с номером записи. Поддержать неполное извлечение: отсутствие одного реквизита не отменяет достоверные остальные. Альтернатива — единый набор регулярных выражений по всему тексту: он плохо различает двух людей и соседние даты/номера.

### 3. Сквозная передача и слияние

Расширить union типов и allow-list ключей в Electron. Пропускать в renderer только проверенный структурированный результат; локальный путь остаётся в main. Расширить `PersonalFormData`, `personalForm`, `PERSONAL_FORM_FIELDS` и список дат для отображения и DOCX. Слияние заполняет только пустые контролы и сохраняет ручные исправления. Новый пользователь очищает новые поля вместе с прежними; список сохранённых пользовательских полей и выбранный шаблон ведут себя как сейчас. Для экспорта дат использовать действующую функцию `formatDate`, расширив её на все новые даты. Альтернатива — отдельная форма и отдельный путь генерации каждого свидетельства: это нарушает модель одного совокупного шаблона.

### 4. Компактные аккордеоны в правой панели

Разместить после текущих персональных и документных полей два независимых аккордеона `Russian Birth Certificate` и `Russian Marriage Certificate`, сохраняя английский язык текущего UI. Заголовок каждого — кнопка с `aria-expanded` и связанной областью; рядом показывать `N of M fields filled` на основе непустых полей без отдельных сохраняемых счётчиков. Внутри рождения сгруппировать поля ребёнка, отца, матери, регистрации и выдачи; внутри брака — супруга 1, супруга 2, регистрации и выдачи. На узком окне поля переходят в один столбец. Оба блока изначально свёрнуты; успешное OCR раскрывает соответствующий блок и не меняет состояние другого. Состояние раскрытия не влияет на FormGroup и не сохраняется между сессиями. Использовать существующие CSS-переменные темы, BEM и видимый фокус.

Альтернатива — вкладки: они скрывают одновременно доступные данные и требуют переключаться между документами при заполнении общего шаблона. Полностью развёрнутые блоки делают длинную правую панель трудно обозримой.

## Risks / Trade-offs

- Различия бланков и качества сканов → несколько вариантов названий реквизитов в фикстурах, проверка по геометрии и `null` для неоднозначных значений.
- Большой контракт из 46 новых полей повышает риск расхождения Python, Electron и формы → единый документированный перечень ключей, контрактные тесты и проверка полного ответа на границе IPC.
- Скан и PDF могут содержать чужие страницы → проверка якорей и совместимости перед объединением; при отсутствии признаков вернуть контролируемую ошибку.
- Текущая кириллическая модель может плохо читать декоративный шрифт или старый бланк → ручная оценка на обезличенных образцах перед выпуском; добавление иной локальной модели допускается только при подтверждённой необходимости.

## Migration Plan

Добавление двух типов и новых полей не требует изменения существующих DOCX-шаблонов: они используют новые плейсхолдеры только по желанию пользователя. При реализации сначала расширить модели и парсеры, затем IPC и генератор, затем форму и аккордеон. Проверить локальный и упакованный OCR, сборку Angular/Electron, генерацию DOCX и регрессию прежних типов. При откате убрать новые типы, поля и парсеры; старые данные текущей сессии не хранятся постоянно, поэтому миграция пользовательского хранилища не нужна.
