# Design

## Context

Мотивация описана в `proposal.md`, поведение — в delta specs. Сейчас оба системных диалога находятся в `electron/main.ts` и не задают `defaultPath`. Main process хранит пути выбранных файлов только до завершения приложения. Постоянного хранилища настроек нет. Angular-форма в `src/app/app.ts` содержит фиксированный набор из 19 контролов; `Новый пользователь` очищает их значения. `generateDocument` получает этот фиксированный набор через preload/IPC, проверяет обязательные строковые поля и передаёт их в Docxtemplater. Неизвестный плейсхолдер оставляется в DOCX как `{name}`.

## Goals / Non-Goals

**Goals:**

- Сохранить два независимых каталога и определения пользовательских полей между запусками без передачи абсолютных путей в renderer.
- Согласованно проверять имена пользовательских полей при создании и при генерации DOCX.
- Держать значения пользовательских полей в той же рабочей сессии, что и существующую общую форму.

**Non-Goals:**

- Сохранение введённых значений и выбранных файлов после перезапуска приложения.
- Привязка пользовательских полей к отдельному DOCX-шаблону, редактирование уже созданных определений или изменение OCR.
- Миграция ранее существующих пользовательских настроек: такого хранилища сейчас нет.

## Decisions

### 1. Локальное хранилище настроек в Electron main

Хранить версионированный JSON с `lastDocumentDirectory`, `lastTemplateDirectory` и массивом `{ label, name }` в `app.getPath('userData')`. Загружать и проверять данные в main process; запись выполнять через временный файл и переименование, сериализуя изменения настроек. Если файл отсутствует, использовать пустые значения. Если отдельная запись некорректна, отбрасывать её без передачи пути в renderer; ошибку чтения или записи показывать как контролируемое сообщение. Это сохраняет данные при штатном закрытии и снижает риск частичной записи. Новая зависимость для настроек не нужна.

Альтернатива — `localStorage` в Angular: он не подходит для абсолютных путей к папкам и разносит настройки между процессами. Отдельный файл для каждой настройки усложнил бы согласованность без пользы для этого объёма данных.

### 2. Две настройки для системных диалогов

Перед вызовом `showOpenDialog` проверять, что сохранённый каталог существует и доступен; только тогда передавать его как `defaultPath`. После успешной проверки и принятия выбранного документа или DOCX-шаблона сохранять `dirname(filePath)` в соответствующем ключе. Отмена, отклонённый файл и ошибка чтения документа не обновляют настройку. Для шаблона проверять расширение `.docx` перед записью. Если каталог исчез, открыть диалог без `defaultPath`; следующее успешное открытие заменит устаревший путь.

Альтернатива — одна общая папка для обоих диалогов: пользователь выбрал раздельное запоминание, поскольку документы и шаблоны могут храниться в разных местах.

### 3. Определения постоянные, значения сессионные

Через узкие IPC-методы renderer запрашивает список определений и отправляет создание или удаление. Main process валидирует ввод и записывает изменение до подтверждения успеха; UI обновляет список по подтверждённому результату. Значения хранятся в динамической группе строковых контролов Angular, не включаются в файл настроек и не передаются в IPC настройки. При старте контролы создаются пустыми. При `Новый пользователь` они очищаются вместе с фиксированными полями, а определения остаются.

Альтернатива — хранить значения вместе с определениями: это противоречит выбранному пользователем поведению и могло бы восстановить данные прошлого пользователя при следующем запуске.

### 4. Устойчивые имена плейсхолдеров и DOCX-контракт

Модальное окно принимает подпись и имя без фигурных скобок, показывает подсказку `{name}`. Подпись обрезается по краям и не может быть пустой. Имя проверяется по `^[A-Za-z][A-Za-z0-9_]*$`; сравнение с фиксированными и уже созданными именами выполняется без учёта регистра. Служебные ключи объектов, например `constructor`, `prototype` и `__proto__`, запрещаются. Проверка повторяется в Electron main, поскольку IPC нельзя доверять. Динамический payload DOCX передаётся отдельно от фиксированного `PersonalFormData`; main process принимает только строковые значения для реально сохранённых имён и объединяет их с фиксированными данными перед рендерингом. Так произвольный IPC-payload не сможет подменить фиксированные поля.

Альтернатива — включать динамические ключи прямо в `PersonalFormData`: это ослабляет проверку полного набора стандартных полей и затрудняет защиту от совпадений имён.

### 5. Отдельный блок и модальное окно Angular

Список пользовательских контролов размещается в отдельном `fieldset` правой панели; каждый элемент показывает `label`, `{name}`, текстовый input и явное удаление. Для создания используется доступное модальное окно с фокусом на первом поле, валидацией на месте и закрытием по отмене. Кнопки внутри формы получают явный `type="button"`. `hasFormValues()` учитывает пользовательские значения, поэтому подтверждение `Новый пользователь` и доступность генерации работают одинаково для всех полей.

Альтернатива — добавлять поля в существующие тематические группы: их назначение произвольно, поэтому отдельный блок лучше соответствует запросу и делает удаление понятным.

## Risks / Trade-offs

- [Папка удалена или недоступна] → проверка перед диалогом и стандартная начальная папка.
- [Ошибка хранения настроек] → атомарная запись, контролируемое сообщение и отсутствие ложного подтверждения создания/удаления поля.
- [Коллизия или вредоносный ключ DOCX] → единая валидация имени в UI и main, запрет служебных ключей, проверка динамического payload перед рендерингом.
- [Долгий список полей] → отдельный блок внутри существующей прокручиваемой панели и проверка доступности модального окна с клавиатуры.

## Migration Plan

При первом запуске после обновления приложение создаёт пустые настройки; существующие данные формы и DOCX-шаблоны не требуют миграции. Развёртывание включает новую локальную запись в каталоге данных приложения. Для отката можно вернуть предыдущую версию приложения: она проигнорирует новый файл настроек, а созданные определения сохранятся для последующего возврата новой версии.
