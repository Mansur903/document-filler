# Spec Delta

## ADDED Requirements

### Requirement: Создание пользовательского поля

Система SHALL позволять создать редактируемое строковое поле через модальное окно с обязательными `label` для отображения и `name` для плейсхолдера DOCX `{name}`. Имя SHALL состоять из латинских букв, цифр и `_`, начинаться с буквы, не совпадать без учёта регистра с именем существующего поля формы или другого пользовательского поля и не быть зарезервированным служебным именем. Система MUST отклонять пустые или недопустимые данные с понятной ошибкой без создания поля.

#### Scenario: Корректное поле создано

- **WHEN** пользователь указывает `label` «Дополнительный телефон» и `name` `extraPhone` и сохраняет модальное окно
- **THEN** в отдельном блоке появляется строковое поле с подписью «Дополнительный телефон» и указанием плейсхолдера `{extraPhone}`

#### Scenario: Создание отменено

- **WHEN** пользователь закрывает модальное окно без сохранения
- **THEN** набор пользовательских полей не меняется

#### Scenario: Имя уже занято

- **WHEN** пользователь указывает имя существующего стандартного или пользовательского поля, включая вариант с другим регистром
- **THEN** система показывает ошибку и не создаёт дублирующее поле

#### Scenario: Данные некорректны

- **WHEN** `label` пуст после удаления пробелов или `name` содержит пробелы, фигурные скобки либо другие недопустимые символы
- **THEN** система показывает ошибку и сохраняет модальное окно для исправления данных

#### Scenario: Указано служебное имя

- **WHEN** пользователь указывает `name` `constructor`, `prototype` или `__proto__`
- **THEN** система показывает ошибку и не создаёт поле

### Requirement: Постоянство и удаление пользовательских полей

Система SHALL сохранять определения пользовательских полей (`label`, `name`) между запусками приложения и показывать их в отдельном блоке общей формы. Текущие значения этих полей MUST NOT восстанавливаться после закрытия и повторного открытия приложения. Пользователь SHALL иметь возможность удалить поле; после удаления его определение и текущее значение MUST исчезнуть из формы и последующих генераций DOCX.

#### Scenario: Приложение запущено повторно

- **WHEN** пользователь создал поле и ввёл в него значение, а затем закрыл и снова открыл приложение
- **THEN** поле с прежними `label` и `name` присутствует, но его значение пусто

#### Scenario: Поле удалено

- **WHEN** пользователь удаляет пользовательское поле
- **THEN** оно исчезает из отдельного блока, не участвует в дальнейшем формировании DOCX и не появляется после перезапуска

#### Scenario: Сохранение определения не удалось

- **WHEN** приложению не удаётся сохранить создание или удаление поля
- **THEN** интерфейс показывает ошибку и не сообщает об успешном применении изменения

## MODIFIED Requirements

### Requirement: Явное начало работы с новым пользователем

Система SHALL предоставлять отдельное действие `Новый пользователь`, которое очищает все значения общей формы, включая значения пользовательских полей, текущий входной документ, состояние распознавания и результат предыдущей генерации, но сохраняет выбранный DOCX-шаблон и определения пользовательских полей. Если в форме есть непустые значения, система SHALL запросить подтверждение перед необратимой очисткой.

#### Scenario: Сброс заполненной формы подтверждён

- **WHEN** пользователь запускает действие `Новый пользователь` при наличии данных и подтверждает очистку
- **THEN** система очищает все значения и состояние текущего пользователя, сохраняя выбранный DOCX-шаблон и набор пользовательских полей

#### Scenario: Сброс заполненной формы отменён

- **WHEN** пользователь запускает действие `Новый пользователь` при наличии данных и отменяет подтверждение
- **THEN** форма, включая значения пользовательских полей, выбранный входной документ и результаты остаются без изменений

#### Scenario: Сброс пустой формы

- **WHEN** пользователь запускает действие `Новый пользователь` при полностью пустой форме
- **THEN** система приводит рабочую область к начальному состоянию без обязательного подтверждения, сохраняя определения пользовательских полей и выбранный DOCX-шаблон

### Requirement: Генерация DOCX из общей формы

Система SHALL передавать в выбранный DOCX-шаблон все существующие паспортные поля и поля `residencepermitID`, `visaID`, `visaValidUntil`, `currentOccupation`, `employer`, `email`, `address`, `phone`, а также текущие значения созданных пользовательских полей по их именам `name`, используя текущие отредактированные значения общей формы. Для паспортной даты `validUntil` и даты разрешения `visaValidUntil` SHALL применяться существующее форматирование даты DOCX.

#### Scenario: Шаблон содержит новые плейсхолдеры

- **WHEN** пользователь генерирует документ из шаблона с новыми плейсхолдерами
- **THEN** каждый плейсхолдер заменяется текущим значением одноимённого поля общей формы

#### Scenario: Шаблон содержит пользовательский плейсхолдер

- **WHEN** шаблон содержит `{extraPhone}`, а в созданном пользовательском поле `extraPhone` введено значение
- **THEN** в готовом DOCX вместо `{extraPhone}` находится текущее значение этого поля

#### Scenario: Поле осталось пустым

- **WHEN** плейсхолдер присутствует в шаблоне, но соответствующее поле общей формы пусто
- **THEN** генератор обрабатывает его по единому действующему правилу для пустых значений и не использует данные из предыдущего пользователя
