# Design

## Context

Мотивация описана в `proposal.md`. Сейчас паспортный parser сначала подтверждает страницу по российской MRZ, затем дополнительно извлекает визуальные поля `Place of Birth` и `Date of Issue` из позиционированных OCR-блоков. Поле органа выдачи отсутствует во всех копиях модели данных, allow-list Electron, общей Angular-форме и DOCX-контракте.

Изменение проходит через Python worker, JSON/IPC-границу, две синхронные TypeScript-модели, Angular-форму и генератор DOCX. Эти слои должны быть обновлены атомарно, иначе строгая типизация или runtime-валидация отклонит результат.

## Goals / Non-Goals

**Goals:**

- Извлекать `authority` только со страницы паспорта, подтверждённой существующей российской MRZ.
- Поддержать подпись `Authority` с inline-значением или отдельным ближайшим значением под подписью без абсолютных координат конкретного изображения.
- Сохранить текущую безопасную семантику частичного OCR: сомнительное значение даёт `null`, а не догадку.
- Провести поле через общую форму, существующее merge/reset-поведение и DOCX без отдельной ветки состояния.

**Non-Goals:**

- Распознавание органа выдачи из MRZ: такого реквизита в MRZ нет.
- Автоматический перевод, исправление названия ведомства или сопоставление с внешним справочником.
- Изменение выбора паспортной страницы, модели PaddleOCR или правил распознавания UAE Residence Permit.
- Добавление отдельного UI-раздела или нового типа документа.

## Decisions

### 1. Извлекать `authority` в существующем паспортном parser

В `parse_passport_data` будет добавлен отдельный визуальный parser поля `Authority`. Он сначала проверит остаток текста после подписи для inline-варианта, затем использует существующее позиционное ранжирование значений под подписью. Подпись `AUTHORITY` войдёт в список визуальных labels, чтобы она не могла быть выбрана как значение другого поля.

Это сохраняет единственную точку формирования `PassportData` и повторно использует проверенную геометрическую логику. Альтернатива с отдельным постпроцессором после `parse_passport_data` отклонена: она дублировала бы обход OCR-блоков и усложнила бы формирование полного пустого результата.

### 2. Считать неоднозначность отсутствующим значением

Parser будет очищать только служебные пробелы по краям и сохранять внутренние пробелы и символы названия. Если подпись отсутствует, подходящего текста нет или ближайшие кандидаты нельзя уверенно различить, `authority` будет `null`.

Выбор первого произвольного текста отклонён, потому что рядом с `Authority` могут находиться дата выдачи и другие паспортные реквизиты. В тестах будут явно представлены inline-, positioned-, missing- и ambiguous-сценарии.

### 3. Расширить единый сквозной контракт строковым полем `authority`

Поле добавляется одновременно в Python `PassportData`, обе копии TypeScript `PassportData` и `PersonalFormData`, паспортный allow-list результата OCR и allow-list payload генерации DOCX. Это сохраняет runtime-проверку полного набора ожидаемых строк и исключает расхождение Electron и renderer.

Опциональное поле только на отдельных границах отклонено: OCR уже выражает отсутствие через `null`, а общая форма — через пустую строку, поэтому отдельная optional-семантика создала бы третий вариант отсутствия.

### 4. Использовать существующие механизмы общей формы

В `personalForm` добавляется пустой строковый control и компактный text input `authority` в группе `Documents`, рядом со страной и датой выдачи. Общая merge-функция автоматически заполнит его только при пустом текущем значении; `personalForm.reset()` автоматически очистит его для нового пользователя.

Отдельная логика merge/reset для `authority` не нужна и отклонена как источник расхождений с остальными полями.

### 5. Передавать `authority` в DOCX без преобразования

Генератор получает строку формы через spread текущего payload и заменяет `{authority}` как обычный текстовый плейсхолдер. Форматирование дат к этому полю не применяется. `README.md` и тестовый DOCX-шаблон будут дополнены новым плейсхолдером.

## Risks / Trade-offs

- [OCR может искажать подпись `Authority`] → нормализовать регистр и разделители тем же способом, что другие визуальные labels, и возвращать `null`, если marker не найден.
- [Значение может оказаться многострочным или быть разделено на блоки] → первоначально выбирать однозначное inline- или ближайшее позиционное значение; реальные новые варианты фиксировать отдельными обезличенными regression-тестами, не ослабляя защиту от соседних реквизитов.
- [Соседняя дата может быть выбрана как authority] → исключать известные labels, MRZ и непригодные кандидаты, а неоднозначность трактовать как отсутствие значения.
- [Несогласованное обновление моделей сломает IPC или DOCX] → обновить все копии и allow-list в одном изменении и проверить Python tests, Angular tests, Electron build и DOCX unit test.
- [Дополнительный input увеличит высоту формы] → использовать существующую компактную сетку и прокрутку панели без изменения layout.

## Migration Plan

1. Расширить OCR-модель и parser вместе с unit-тестами поля `authority`.
2. Обновить TypeScript-контракты и runtime allow-list на Electron-границах.
3. Добавить control/input и проверить существующие правила merge и reset.
4. Расширить DOCX payload, тестовый шаблон и документацию.
5. Выполнить Python, Angular, DOCX и production build проверки.

Персистентного хранилища и миграции пользовательских данных нет. Откат выполняется удалением нового поля из тех же сквозных контрактов; существующие шаблоны без `{authority}` остаются совместимыми.
