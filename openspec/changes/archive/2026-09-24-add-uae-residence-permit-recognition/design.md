# Design

## Context

См. `proposal.md` для мотивации и delta-specs для наблюдаемого поведения.

Сейчас Angular-компонент хранит один `passportForm`, при принятии нового файла сбрасывает форму и вызывает узкий preload API без аргумента типа документа. Electron main хранит единственный абсолютный путь, передаёт его в Python-скрипт `recognize_passport.py`, а TypeScript-сервис проверяет фиксированный ответ `PassportData`. Python использует PaddleOCR локально, для паспорта выбирает PDF-страницу по MRZ и возвращает JSON с десятью полями. Генератор DOCX валидирует тот же фиксированный набор и форматирует три даты.

Изменение пересекает Angular, preload/IPC, Electron main, Python OCR, автономную сборку и DOCX-модель. Абсолютный путь к документу должен по-прежнему оставаться в main process; renderer получает только безопасные метаданные и превью. Приложенный образец является UAE Residence Permit, хотя в пользовательском описании он назван Emirate ID; извлечение проектируется по фактическим английским подписям на образце, без сохранения персональных значений образца в репозитории.

## Goals / Non-Goals

**Goals:**

- Сохранить локальную архитектуру Angular → preload → Electron main → OCR worker и одинаковое поведение в development и упакованном приложении.
- Явно маршрутизировать один выбранный файл в паспортный или UAE Residence Permit parser.
- Сделать результат OCR частичным типизированным патчем к общей форме и централизовать правило «заполнять только пустое».
- Извлекать значения UAE Residence Permit по семантическим подписям и геометрии OCR-блоков, а не по абсолютным пиксельным координатам одного изображения.
- Сохранить все существующие паспортные плейсхолдеры, добавить независимый `visaValidUntil` для срока UAE Residence Permit и поддержать любой порядок распознавания документов без миграции пользовательских данных.

**Non-Goals:**

- Распознавание пластиковой Emirates ID card, виз других форматов или произвольных UAE-документов.
- Автоматическое определение типа документа, распознавание имени, номера паспорта, места/даты выдачи или фотографии из UAE Residence Permit.
- Валидация формата email, телефона или адреса сверх хранения редактируемой строки.
- Сохранение профилей пользователей между запусками приложения или история распознаваний.
- Загрузка документов во внешний сервис, обучение собственной OCR-модели или добавление UI-библиотеки только ради нового layout.

## Decisions

### Обобщить контракт вокруг типа документа

Ввести общий discriminated type документа (`passport` и `uaeResidencePermit`) и нейтральные модели выбранного файла/результата распознавания в обеих копиях TypeScript-моделей. Angular передаёт выбранный тип в preload-вызов распознавания; Electron main проверяет значение по allow-list и связывает его с удерживаемым локальным путём до запуска worker. Каналы и методы с паспортными именами переименовываются в нейтральные согласованно во всех слоях.

Тип можно переключить после выбора файла, поэтому он передаётся при распознавании, а не навсегда записывается в результат диалога выбора. Автоопределение отвергнуто: два поддерживаемых документа имеют разные признаки, а ошибочная классификация может незаметно записать значения не в ту группу полей.

### Использовать единый OCR worker с отдельными парсерами

Точка входа worker принимает проверенный тип документа и поддерживаемый путь, один раз запускает PaddleOCR, затем передаёт OCR-блоки в существующий MRZ-парсер паспорта либо новый parser UAE Residence Permit. Для PDF результаты остаются разделёнными по страницам: паспорт сохраняет MRZ-выбор, а разрешение использует первую страницу, на которой найдены необходимые английские подписи.

Два самостоятельных executable отвергнуты из-за дублирования тяжёлой OCR-инициализации, PyInstaller-конфигурации и IPC-кода. Полная замена существующего паспортного parser отвергнута: его MRZ-валидация остаётся наиболее надёжным источником паспортных полей.

### Извлекать разрешение по якорям и относительной геометрии

Новый parser нормализует OCR-текст подписей (`UID No`, `File No`, `Expiry Date`, `Profession`, `Employer`) без учёта регистра, пунктуации и межсимвольных пробелов. Для каждой подписи он ранжирует соседние не-label блоки по относительной геометрии: значения на той же строке слева имеют первый приоритет, значения непосредственно над/под подписью — fallback. Идентификаторы дополнительно фильтруются по цифровому/разделённому виду, дата проходит календарную проверку, текст профессии и работодателя очищается только по краям.

Абсолютные координаты и crop-зоны отвергнуты, потому что они ломаются при другом разрешении, масштабе и полях скана. Поиск по одной склеенной OCR-строке отвергнут, потому что двуязычный фон и соседние подписи теряют пространственную связь. Parser возвращает `null` при неоднозначности вместо подстановки ближайшего текста.

### Представлять OCR как частичный патч к общей форме

Создать единую `PersonalFormData` со всеми существующими полями и новыми `residencepermitID`, `visaID`, `visaValidUntil`, `currentOccupation`, `employer`, `email`, `address`, `phone`. Ответ каждого parser содержит только его поддерживаемые nullable-поля: паспортный parser возвращает `validUntil`, а parser UAE Residence Permit — отдельный `visaValidUntil`. В Angular одна чистая merge-функция проходит по ключам OCR-ответа и записывает значение только когда текущее поле равно пустой строке, а новое значение после проверки не пусто.

Централизация merge-правила предотвращает различия между типами документов и позволяет отдельно протестировать оба порядка распознавания, потенциальные будущие пересечения полей, ручные изменения и `null`. Так как ответы содержат только поля своего документа, последовательности паспорт → разрешение и разрешение → паспорт приводят к одной и той же совокупной форме. `setValue()` всего ответа отвергнут, потому что он очищает данные отсутствующими полями; безусловный `patchValue()` отвергнут, потому что перезаписывает ранее распознанные и ручные значения.

### Сделать форму постоянной компактной правой колонкой

Основной экран остаётся двухколоночным на широком окне: слева находятся тип документа, выбор/превью/распознавание и блок DOCX, справа — всегда видимая общая форма. Правая панель получает ограничение по доступной высоте и внутренний `overflow-y: auto`; поля группируются на «Личные данные», «Документы» и «Контакты», используют уменьшенные интервалы и двухколоночную сетку там, где ширина позволяет. На узком экране layout становится одноколоночным, а ограничение внутренней высоты снимается, чтобы не создавать вложенную неудобную прокрутку.

Для «Нового пользователя» используется компактное двухшаговое подтверждение внутри панели, а не новая UI-зависимость. Сброс очищает форму, выбранный входной файл, ошибки/статусы OCR и результат генерации; выбранный DOCX-шаблон сохраняется как не относящаяся к конкретному пользователю настройка.

Скрытие формы до первого OCR отвергнуто, потому что ручные контактные поля должны быть доступны заранее. Отдельные формы для каждого документа отвергнуты, потому что создают дублирование общих полей и не дают однозначного источника данных для DOCX.

### Корректно различать MIME-типы превью и расширить allow-list

Общий allow-list в Electron и Python включает `.jpg`, `.jpeg`, `.png`, `.pdf`. Для PNG Electron формирует `data:image/png`, для JPEG — `data:image/jpeg`; PDF по-прежнему не передаётся в renderer целиком. Проверка расширения сохраняется в main process и worker, чтобы renderer не мог обойти ограничения IPC-вызовом.

Передача содержимого всех файлов в renderer отвергнута из-за ненужного расхода памяти и расширения доверенной поверхности. Определение PNG как JPEG отвергнуто, потому что текущая жёстко заданная строка media type создаст некорректный data URL.

### Расширить DOCX-контракт вместе с общей моделью

Валидатор IPC генерации принимает полный `PersonalFormData` и проверяет строковый тип каждого поля. Генератор передаёт новые поля напрямую, а независимые `validUntil` и `visaValidUntil` форматирует как `DD.MM.YYYY`. Незаполненные строки не получают значения из предыдущего пользователя и рендерятся по текущему поведению Docxtemplater.

Отдельная модель только для новых плейсхолдеров отвергнута: она усложняет IPC и создаёт два источника истины для одной формы. `residencepermitID` сохраняется в точном регистре, запрошенном для DOCX-плейсхолдера, несмотря на менее обычное именование.

## Risks / Trade-offs

- **[Шумный двуязычный фон и низкий контраст ухудшат чтение подписей]** → Нормализовать подписи, использовать геометрическое ранжирование и тесты на OCR-блоках; при неоднозначности возвращать `null`, не угадывать.
- **[Варианты верстки UAE Residence Permit могут размещать значения иначе]** → Не использовать абсолютные координаты, покрыть горизонтальный и вертикальный варианты соседства и ограничить область кандидатов относительно размера label-блока.
- **[Разный порядок распознавания может дать различающееся состояние при ошибке merge-логики]** → Разделить `validUntil` и `visaValidUntil`, применять один общий merge-helper и покрыть обе последовательности симметричными тестами.
- **[Большое число полей ухудшит обзор]** → Семантические группы, компактные интервалы, sticky-заголовок/действие сброса при необходимости и прокрутка только правой панели на широком экране.
- **[Переименование IPC может временно рассинхронизировать слои]** → Изменить обе модели, constants, preload, main, Angular и тесты одним атомарным этапом, затем запустить обе TypeScript-сборки.
- **[PNG или новый parser могут отсутствовать в `ocr.exe`]** → Проверить standalone build на PNG-образце и UAE fixture без установленного Python и сети; обновлять PyInstaller collection только при фактической нехватке ресурса.
- **[Реальный образец содержит персональные данные]** → Не копировать его в тестовые fixtures или артефакты; использовать обезличенные OCR-блоки и проводить ручную проверку с исходным файлом вне репозитория.

## Migration Plan

1. Ввести обобщённые document types, форму и IPC-контракты, сохранив набор существующих паспортных полей.
2. Обобщить выбор/распознавание файла, добавить PNG и корректный MIME preview, затем подключить тип документа.
3. Добавить UAE Residence Permit parser и маршрутизацию worker с модульными тестами на обезличенных OCR-блоках.
4. Перестроить Angular layout и merge/reset-поведение, обновить компонентные тесты.
5. Расширить DOCX-валидацию, документацию плейсхолдеров и интеграционные проверки.
6. Собрать Angular/Electron, автономный OCR worker и Windows-пакет; вручную проверить последовательности паспорт → разрешение и разрешение → паспорт, затем ручные контакты и DOCX.

Откат выполняется возвратом изменения: постоянных пользовательских данных и мигрируемого формата хранения нет. Старые DOCX-шаблоны остаются совместимыми, потому что существующие плейсхолдеры и формат дат сохраняются.
